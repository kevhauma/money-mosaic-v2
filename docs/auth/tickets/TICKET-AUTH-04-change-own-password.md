# TICKET-AUTH-04 — Change your own password, and stop the default admin password being forgotten

- **Area:** Auth & Accounts
- **Released in:** _unreleased_
- **Type:** Feature
- **Traceability:** new; planned for v3

## User story

As any signed-in user, I want to change my own password without asking the administrator, so an admin reset is the fallback rather than the only route.

## Description

Self-service password change in Settings, plus a standing reminder while the seeded `admin` account still has the password `admin` — the one credential every installation of this app shares.

## Current situation (as-is)

- [TICKET-AUTH-01](./TICKET-AUTH-01-users-seeded-admin-login.md) seeds `admin` / `admin` and [TICKET-AUTH-03](./TICKET-AUTH-03-admin-user-management.md) lets an **admin** set anyone's password, including their own. There is no way for a **non-admin** to change their own password, and nothing anywhere signals that the default password is still in place.
- The Settings page (`feature-settings`) is the established home for per-user preferences and already hosts embedded sections rather than sub-routes (see [TICKET-DAT-04](../../data-management/tickets/TICKET-DAT-04-commit-to-embed-set06-repair.md)).

## Desired result (to-be)

- **`POST /api/auth/password`** — `{ currentPassword, newPassword }` for the signed-in user. A wrong `currentPassword` returns **401**; an empty `newPassword` returns 400. On success it stamps `passwordUpdatedAt` and **keeps the caller's own session alive** while deleting that user's _other_ sessions, so changing your password does not log you out of the tab you are typing in but does end the session on the machine you were worried about.
- **An "Account" section on the Settings page** showing the signed-in email, display name and role, with a change-password form (current, new, confirm). It reports success inline and clears all three fields.
- **Display name** is editable here too — the one field a non-admin can change about themselves.
- **Default-password reminder**: while the `admin` account's `passwordUpdatedAt` still equals its `createdAt` (i.e. the seeded password was never changed), the app shows a dismissible-per-session banner to **admins only**, linking to the Account section. `GET /api/auth/me` carries a `usingDefaultPassword` boolean so the client does not have to guess.
- **No forced change**: the banner nags, it does not block. This is a deliberately unsecured local-hosting setup, and someone who wants `admin`/`admin` on their own LAN keeps it.

## Notes

- **The banner is the whole reason this ticket is not just "a form".** Every installation of this app ships with the same known credentials; a quiet, persistent, admin-only reminder is the cheapest honest answer that does not contradict the deliberately-unsecured brief. See the non-goals list in [TICKET-AUTH-01](./TICKET-AUTH-01-users-seeded-admin-login.md).
- Keeping the calling session alive while killing the others is the behaviour people expect from "I think someone else is logged in as me" — the only realistic reason to change a password on a LAN box.
- Depends on [TICKET-AUTH-02](./TICKET-AUTH-02-login-screen-session-guard.md) for the session store and [TICKET-AUTH-01](./TICKET-AUTH-01-users-seeded-admin-login.md) for hashing. Independent of the SRV data-migration tickets — it can ship as soon as the login screen exists.

### Implementation notes (2026-09-28)

Decisions the ticket left open, taken while building it:

- **The display-name endpoint is `PATCH /api/auth/me`.** The to-be section asked for the field without naming a route; patching the resource `me` already answers for is the obvious REST shape, and it keeps the self-service surface to two routes.
- **`usingDefaultPassword` describes the _asking_ account, not the installation.** It is `true` only when the row is the seeded `admin` identifier _and_ `passwordUpdatedAt === createdAt`. The timestamps alone would flag every freshly created account (an admin choosing a colleague's first password has not left a shared secret behind), and a global "the admin account is still default" flag would nag a second admin who cannot fix it — resetting someone else's password is [TICKET-AUTH-03](./TICKET-AUTH-03-admin-user-management.md)'s job. The client still checks `role === 'admin'` explicitly, so the criterion's wording holds even if the flag's rule ever widens.
- **`POST /api/auth/login` now answers with `SessionUser` too**, not just `me` — otherwise a fresh sign-in could not show the banner without a second round trip, which is exactly the moment it matters. That widened a response TICKET-AUTH-01 specified as `PublicUser`; its criterion has been annotated rather than left to read as though nothing changed. `POST /password` and `PATCH /me` answer with the same shape, which is what lets the banner disappear and the sidebar rename themselves without re-fetching.
- **The banner links to `/settings` plainly, and the Account section was moved to the top of that page.** The router is configured without `withInMemoryScrolling`, so a `#fragment` would not scroll to anything — a dead anchor pretending to be a deep link is worse than a link that lands on the section because the section is first.
- **Dismissal is in-memory session state** (a `SessionStore` key inside `ANONYMOUS`), deliberately not persisted: a reminder about a password everyone knows should not be able to go quiet for good on one click.
- **Found while building, fixed in review: the login form could not sign in the seeded admin.** It applied `Validators.email` to the identifier, but the seeded identifier is literally `admin` — rejected before anything was sent, so _no one could sign in to a fresh database at all_. The server treats the field as free text on purpose ([`server/src/schema/users.ts`](../../../server/src/schema/users.ts) says so), so the form was the side that was wrong. Raised with the user, who chose to relax the validator rather than reshape the seed; [`login-page.component.ts`](../../../src/app/feature-auth/components/login-page/login-page.component.ts) now keeps only `Validators.required`, with a comment saying why. TICKET-AUTH-02 shipped it and no criterion of this ticket asked for it, hence the note here rather than a silent fix.

### Review notes (2026-09-28)

Changed after the `conventions-reviewer` pass, before the commit:

- **The interceptor's exemption for this endpoint is now keyed on a `code`, not the URL.** `POST /api/auth/password` answers 401 for _two_ different reasons — its own "wrong current password", and `requireAuth` in front of it saying "your session expired" — so exempting the URL outright swallowed the second one, leaving someone typing into a form backed by a dead cookie, told only "Not signed in", with nothing to send them to the login screen. The route now tags its own answer `wrong_current_password` and only that code is exempt; `httpError` takes an optional code and `ErrorBody` carries it, withheld for 5xx for the same reason the message is (better-sqlite3 throws `code: 'SQLITE_CONSTRAINT_UNIQUE'`). The convention in `coding-conventions/SKILL.md` was reworded to match — exempt by URL only where a 401 can mean nothing else.
- **`login()` resets the banner dismissal.** `/login` is reachable with a live session, so one admin dismissing the reminder would otherwise hide it from the next admin who signed in over the top.
- **The password form became its own component** ([`account-password-form/`](../../../src/app/feature-settings/components/account-password-form/)). The combined section was a 139-line template at 15 cyclomatic / 23 cognitive — the most complex in the feature by a factor of two — and it was carrying two forms that share a heading and nothing else. Renaming and re-passwording now have a component and a spec each (74-line template, 11/12).
- The banner's layout was rebuilt around one child: daisyUI 5's `.alert` is a grid, so the `flex-wrap`/`flex-1` utilities on it were no-ops and the buttons could never wrap under the sentence.
- **The login field says what it takes.** Relaxing the validator fixed the function; the legend still read `Email`, with `type="email"` and a `you@example.com` placeholder, on an installation whose only account is `admin`. It is now `Email or username` / `type="text"` / placeholder `admin`, and a spec pins the actual regression — signing in with the bare `admin` identifier. (`type="email"` never re-imposed the rule at the browser layer: `ReactiveFormsModule` puts `novalidate` on the form.)
- **A 5xx no longer quotes itself onto a form.** `authErrorMessage` returned `body.error` for any status, and every 5xx body is the literal "Internal server error" — which says nothing about the form it appears on. It now falls through to the caller's wording, which at least names the action that failed; the store spec's mock carries a real 500 body instead of none, so the path is actually pinned.
- Smaller: the confirm field's `ariaInvalid` no longer reads the whole form's validity, the rename's failure path has a component-level case, the banner's grid child is a `<div>` (it held a `<p>`, which a `<span>` may not), `usingDefaultPassword` compares through `normaliseEmail` and documents the two ways it can under-report, the composition spec asserts the new first section, and the section is not exported through the feature barrel (its five siblings are not either — only the routed page is).
