# TICKET-STAT-29 — Spending heatmap: top categories × day of week

- **Area:** Dashboard
- **Released in:** [v2.1 Extra graphs](../../releases/v2.1_extra_graphs/overview.md)
- **Type:** Feature
- **Traceability:** new capability, adds **FR-STAT-15**. Closest existing requirement is FR-STAT-10 (weekday/weekend split, shipped by [TICKET-STAT-06](./TICKET-STAT-06-weekday-weekend-split.md)), which answers the same "when do I spend" question with two numbers and no category dimension. Graduated from the "Extra graphs" idea in [v9999_ideas/requirements.md](../../v9999_ideas/requirements.md).

## User story

As someone reviewing my spending, I want a heatmap of my biggest categories against the days of the week, so I can see *which* category burns money on *which* day instead of reading one flat total per category and one weekday-vs-weekend ratio that hides both.

## Description

Adds a new Dashboard row rendering an ECharts cartesian heatmap: one row per top-4 expense category (plus an "Other" row folding the rest), one column per day of the week, each cell coloured by the total spent in that category on that day of the week across the selected range. This ticket ships the day-of-week cycle only; [TICKET-STAT-30](./TICKET-STAT-30-heatmap-cycle-switcher.md) adds the other cycles.

## Current situation (as-is)

- [weekday-weekend-split.ts](../../../src/app/core/stats/weekday-weekend-split.ts)'s `computeWeekdayWeekendSplit` is the only "cyclical time" aggregate in `core/stats/`: it buckets expense into exactly two day types and returns per-day averages. It has no category dimension, and its panel ([weekday-weekend-split-panel.component.ts](../../../src/app/feature-dashboard/components/weekday-weekend-split-panel/weekday-weekend-split-panel.component.ts)) draws two CSS bars, not a chart.
- [category-composition-trend.ts](../../../src/app/core/stats/category-composition-trend.ts)'s `computeCategoryCompositionTrend` does produce per-bucket per-category series, but its buckets are *chronological* (`bucketKeysInRange(from, to, granularity)` from [date-buckets.ts:117](../../../src/app/shared/utils/date-buckets.ts)) — every January Monday is its own column, so it can't fold "all Mondays" together. Nothing in `core/stats/` maps a date onto a *position within a repeating cycle*.
- [echarts-setup.ts](../../../src/app/shared/echarts/echarts-setup.ts) registers `PieChart`/`BarChart`/`LineChart` plus `Tooltip`/`Grid`/`Legend`/`DataZoom`/`CanvasRenderer` only — there is no `HeatmapChart` and no `VisualMapComponent`, so a heatmap cannot render at all today.
- Dashboard rows are a closed union: `DashboardRowId` and `DEFAULT_DASHBOARD_ROW_ORDER` at [app-db.ts:395-414](../../../src/app/core/data-access/app-db.ts), human labels in [dashboard-row-order.ts:3-12](../../../src/app/feature-dashboard/dashboard-row-order.ts), and the render switch in [dashboard-overview.component.html](../../../src/app/feature-dashboard/components/dashboard-overview/dashboard-overview.component.html). `resolveDashboardRowOrder` already appends ids that a saved layout doesn't know about, so adding a row does not break an existing user's persisted order.
- [chart-theme.ts](../../../src/app/shared/echarts/chart-theme.ts) exposes `resolveChartCategoricalColors()` (a fixed-order *categorical* palette per theme) and `CHART_NO_COLOR_FALLBACK`. There is no sequential/continuous scale — every chart so far has been categorical.

## Desired result (to-be)

- New pure aggregate `core/stats/category-cycle-heatmap.ts`:
  ```ts
  computeCategoryCycleHeatmap(
    transactions, categoriesById, from, to,
    cycle: 'day-of-week',            // widened by TICKET-STAT-30
    ownSavingsIbans, accountsById,
    topN = 4,
  ): CategoryCycleHeatmap
  ```
  returning `{ columns: { key: string; label: string }[]; rows: HeatmapRow[]; cells: { rowIndex: number; columnIndex: number; amount: number }[]; maxAmount: number }`, where `HeatmapRow` carries `{ categoryId: number | null; name: string; color: string; total: number }`.
- Every per-transaction decision goes through `classifyForStats()` — only `kind: 'expense'` accumulates, so the heatmap can never disagree with the stat cards about what an expense is. The cell is chosen from the transaction's own `bookingDate`, using the same UTC calendar convention as `weekday-weekend-split.ts`'s `isWeekendDate`.
- Rows are the top `topN` categories by total expense in range, in descending order, plus a single `Other` row folding every remaining category *and* uncategorised spend (`categoryId: null`). `Other` is omitted when nothing falls into it. Row colour is the category's own `color`, falling back to `CHART_NO_COLOR_FALLBACK`.
- Columns for `'day-of-week'` are Mon–Sun, always all seven, in that order — a day with no spend renders as a zero cell rather than a missing column.
- New `resolveChartHeatmapColors(): string[]` in [chart-theme.ts](../../../src/app/shared/echarts/chart-theme.ts) returning a 2–3 stop sequential ramp for the active `data-theme`, fed to the chart's `visualMap.inRange.color`. Derived from the theme's own categorical palette (an "empty" tone through the theme's leading accent), so a new theme gets a sensible ramp for free rather than a hardcoded blue.
- [echarts-setup.ts](../../../src/app/shared/echarts/echarts-setup.ts) additionally registers `HeatmapChart` and `VisualMapComponent`, with its existing comment extended to say why (one shared registration point; both modules are small and echarts already lives only in lazy feature chunks, so `angular.json`'s `initial` budget is untouched).
- New `app-spending-heatmap-panel` under `feature-dashboard/components/spending-heatmap-panel/`, following the existing panel shape: `mm-paper` wrapper, `NgxEchartsDirective`, `OnPush`, a pure option-builder function kept outside the class so it is testable without `TestBed` (same as `buildColumnChartOption` in [trend-chart-panel.component.ts:55](../../../src/app/feature-dashboard/components/trend-chart-panel/trend-chart-panel.component.ts)), and range read as `rangeStore.from('dashboard')`/`to('dashboard')`.
- New row id `'spending-heatmap'`, appended to `DashboardRowId` and to the end of `DEFAULT_DASHBOARD_ROW_ORDER`, with the label `'Spending heatmap'` in `DASHBOARD_ROW_LABELS` and a `@case` in the Dashboard's row switch. Appended, not inserted, so an existing saved `rowOrder` gains it at the bottom via `resolveDashboardRowOrder` instead of shuffling the user's layout.
- The panel hides itself when there is no expense in range (renders nothing rather than an all-zero grid), the same self-hiding convention `visibleDashboardRows`'s doc comment already describes.
- Clicking a cell navigates to `/transactions` with `buildTransactionDrilldownParams({ from, to, categoryId })` for the panel's range and that row's category (`UNCATEGORISED_SENTINEL` for the uncategorised part of `Other` is *not* used — `Other` is a fold of several categories and drills down to the range only). The day-of-week half of the selection is not expressible in the existing transaction query params; see Notes.
- A visually-hidden table mirrors the grid's figures (rows × columns × formatted amounts) with the canvas host carrying `role="img"` and a summary `aria-label`, exactly as [TICKET-STAT-20](./TICKET-STAT-20-trend-chart-accessible-numbers.md) established for the other charts.
- Privacy mode (`AppSettingsStore.privacyModeEnabled`) suppresses figures: the tooltip shows the category and day but not the amount, and the sr-only table's amounts are blurred via `mm-privacy-blur`. Cell *colour* stays, since intensity is a proportion, not a figure — the same line [TICKET-PRIV-01](../../settings/tickets/TICKET-PRIV-01-privacy-mode-dashboard.md) drew for the weekday/weekend bars.

> **Implementation note, 2026-08-05 — privacy mode *withholds* the screen-reader figures instead of
> blurring them.** The to-be above says the sr-only table's amounts are wrapped in
> `mm-privacy-blur`; they are not. `.sr-only` clips the table to a 1px box, so a CSS blur filter
> paints nothing, and a blur has never hidden anything from a screen reader — it would have read
> every amount out loud with privacy mode on. `accessibleRows` now emits the literal `hidden` in
> place of each amount while privacy mode is on, and the panel no longer imports
> `PrivacyBlurComponent` at all (it has no visible figures of its own — the colour scale, which
> carries the only on-screen amounts, is removed entirely). Caught in convention review; the
> acceptance criterion below is unchanged, since it always asked for "no amount legible", not for a
> particular mechanism.

## Notes

- **Day-of-week is not expressible in the transaction filter.** `buildTransactionDrilldownParams` ([search-params.ts:19](../../../src/app/shared/utils/search-params.ts)) supports `from`/`to`/`categoryId`/`accountId` only, and the Transactions page has no "day of week" filter. Rather than inventing a query param and a filter control inside a chart ticket, the drilldown deliberately drops the day dimension and filters by range + category. A real weekday filter is a Transactions-feature ticket, noted in the version's "Considered, not ticketed yet".
- **Top-4, not top-5.** The other composition charts cap at top-5; four rows plus `Other` keeps the grid legible at panel height (5 rows × 7 columns) and matches the idea's own "top 4 categories rows" wording.
- **Averages vs. totals.** Cells are *totals*, not per-occurrence averages: a range covering 9 Mondays and 8 Tuesdays makes Monday look slightly heavier for free. This is the same simplification the existing weekday/weekend panel deliberately avoids (it divides by day count) — mentioned here so the difference is a recorded decision, not an oversight. A per-occurrence-average toggle is follow-up scope.
- Independent of every EXP ticket in this version — no route, no new feature area, no schema change.
