# TICKET-TRF-05 — High-confidence matching links my own transfer leg, not a co-owner's same-amount contribution

- **Area:** Transfers
- **Released in:** [v1.1 Joint accounts](../../releases/v1.1_joint_accounts/overview.md)
- **Type:** Bug fix
- **Traceability:** fixes FR-TRF-3 / FR-TRF-5; completes [TRF-03](./TICKET-TRF-03-guard-partner-inflow-matching.md)'s to-be (neutral excluded from *all* auto-matching); protects [CAT-02](../../categories/tickets/TICKET-CAT-02-neutral-category-kind.md) + [STAT-46](../../dashboard/tickets/TICKET-STAT-46-contribution-net-worth.md)

## User story

As someone with a shared account, I want my transfer into the joint pot to link to **my own** deposit leg rather than to a co-owner's same-amount contribution that happened to land nearby, so my contribution stake stays right and their money isn't swallowed into one of my transfers.

## Description

[TRF-03](./TICKET-TRF-03-guard-partner-inflow-matching.md) keeps suspected contributions out of the medium-confidence pool but deliberately leaves the high-confidence IBAN path untouched. That path corroborates a pair when **either** side's `counterpartyIban` names the other's account — so an outflow of mine that merely says "counterparty = the joint account" is confirmed against *any* same-amount credit booked on that joint account, my partner's contribution included. It then picks closest-by-date with no uniqueness requirement, so the wrong leg wins whenever the contribution is nearer in date than my real one. This ticket makes mutual corroboration outrank one-sided corroboration, and finally excludes `neutral`-tagged transactions from every matching pass.

## Current situation (as-is)

- `ibanConfirms` ([transfer-matching.ts:49-59](../../../src/app/core/transfers/transfer-matching.ts)) is satisfied by **one** side: `(!!aIban && aIban === accountIban(b)) || (!!bIban && bIban === accountIban(a))`. It never checks whether the other side points back, so a candidate's own `counterpartyIban` is ignored entirely when the first side already names its account.
- `findHighConfidenceMatches` ([transfer-matching.ts:136-169](../../../src/app/core/transfers/transfer-matching.ts)) collects every `ibanConfirms` candidate in the abs-amount bucket and links the **closest by date** — unlike the medium pass it has no mutual-uniqueness gate, and it consumes greedily in list order.
- `isExternalContribution` ([transfer-matching.ts:99-115](../../../src/app/core/transfers/transfer-matching.ts)) is only applied when building `remaining` for the medium pass ([transfer-matching.ts:234-244](../../../src/app/core/transfers/transfer-matching.ts)). The high-confidence pass runs *before* it, on the unfiltered list.
- **Root cause, concretely.** Joint account `J`, my checking `C`. `T1` = `C −500`, `counterpartyIban = J`. `T2` = `J +500`, `counterpartyIban = C` (my real leg). `T3` = `J +500`, `counterpartyIban =` a co-owner's IBAN (their contribution). `ibanConfirms(T1, T3)` is **true** on `T1`'s side alone (`J === accountIban(T3)`), so `T3` sits in the same candidate list as `T2` and wins on date proximity. Worse, iteration order can decide it first: `T3` is itself scanned against `T1` and confirms from the other direction, links immediately, and consumes `T1` before `T2` is ever considered — leaving my genuine leg unlinked and the contribution booked as one side of my transfer.
- The same one-sidedness fires when the contribution carries **no** counterparty IBAN at all (a bank that omits it): `T1`'s pointer at `J` is enough on its own.
- TRF-03's to-be says a `neutral`-tagged transaction is "excluded from **all** auto-matching" ([TRF-03 to-be](./TICKET-TRF-03-guard-partner-inflow-matching.md)), but its acceptance criterion narrowed that to the medium pool and the code follows the criterion — so once you tag a deposit "Partner contribution", a later run can still re-link it at high confidence. The spec that claims to cover this, `'excludes a neutral-tagged inflow from all auto-matching'` ([transfer-matching.spec.ts:403](../../../src/app/core/transfers/transfer-matching.spec.ts)), uses IBAN-less fixtures and so never exercises the high path.

## Desired result (to-be)

- High-confidence matching runs in **two tiers**, both still IBAN-driven:
  1. **Mutual corroboration** — both legs' `counterpartyIban` name each other's account. Strongest evidence; resolved first, across all transactions, before any one-sided pass gets a turn.
  2. **One-sided corroboration** — today's behaviour, on what tier 1 left. Within a bucket, candidates that `isExternalContribution` flags are used **only when no unflagged candidate exists**, so a co-owner's contribution can never beat my real leg on date proximity.
- A `neutral`-tagged transaction is excluded from **every** pass — high and medium, in either role. The user has said "this is a contribution"; that outranks any IBAN inference.
- Precedence from TRF-03 is preserved: a co-owner IBAN that is *also* a registered own-account IBAN still links via the own-account path, because mutual corroboration is evaluated before the contribution guard is consulted.
- Nothing changes for a household with one same-amount credit in the window: a single IBAN-confirmed candidate links exactly as it does today, at high confidence.

## Acceptance criteria

**Implementation note (2026-08-14):** the one-sided tier orders *initiators* as well as candidates —
a suspected contribution only gets to initiate a link after every unflagged transaction has had its
turn — which is what makes the outcome independent of input order. The side effect is that in the
co-owner-IBAN-also-own-account case the emitted `from`/`to` **orientation flips** (the own-account
leg initiates, so it becomes `from`). That orientation was never meaningful — it has always been
whichever leg the input array happened to list first — so criterion 7 below now asserts the *pair*
rather than its direction. See the last Note for the one place the orientation is user-visible.

- [x] `ibanConfirms` (or a sibling predicate) distinguishes **mutual** corroboration (each side's `counterpartyIban` names the other's account) from **one-sided** corroboration, keeping `normalizeIban` on both sides per [TRF-04](./TICKET-TRF-04-normalize-iban-matching.md). (`ibanCorroboration` returning `'mutual' | 'one-sided' | 'none'`, built on `namesAccountOf`, which normalizes both sides — [transfer-matching.ts:57-84](../../../src/app/core/transfers/transfer-matching.ts); the TRF-04 spacing/case specs still pass.)
- [x] `findHighConfidenceMatches` resolves every mutually-corroborated pair first and only then runs the one-sided pass over what remains unconsumed — so iteration order can no longer let a one-sided confirmation consume a leg that has a mutual partner. (`linkMutualPairs` then `linkOneSidedPairs`, [transfer-matching.ts:207-269](../../../src/app/core/transfers/transfer-matching.ts); proved order-independent by the both-orderings assertions in `'links my own two legs and leaves a co-owner contribution unlinked, whatever the input order'`.)

## Notes

- Deliberately **not** widening the guard itself: `isExternalContribution` keeps its `joint`-account and `amount > 0` conditions ([transfer-matching.ts:109-110](../../../src/app/core/transfers/transfer-matching.ts)). A contribution into a non-joint account is a separate, larger question about what "external" means outside a shared pot.
- Also **not** in scope: surfacing the losing one-sided candidates as `ambiguous` for manual confirmation. Today a one-sided pass silently picks a winner; making it defer to the user when several plausible legs exist is a UX change, not a correctness fix, and would change what the transfers review list contains.
- The tier-1/tier-2 split subsumes TRF-04's benefit rather than replacing it: normalization stays at comparison time, both tiers.
- Reported from real data after TRF-03 shipped — the guard works for the medium path it was scoped to, so this is a follow-on rather than a defect in TRF-03's own implementation.
- **Where the `from`/`to` orientation is user-visible.** `Transfer.fromTransactionId`/`toTransactionId` are persisted, and the attribution-override fieldset labels its reimbursement picker with the **from**-leg's date ([attribution-override-fieldset.component.ts:119-125](../../../src/app/feature-transactions/components/attribution-override-fieldset/attribution-override-fieldset.component.ts)), so for a newly-linked pair in the flagged-initiator case that label can now show the other leg's date (at most `matchWindowDays` apart). Everything else that reads a transfer treats the two legs symmetrically. Already-stored transfers are untouched — the matcher only ever runs on unlinked transactions. Normalising orientation properly (debit always `from`) would be a better fix and a wider one: it changes the medium path too, so it belongs in its own ticket.
- The two suspicion checks now run **once per transaction per matcher run** rather than once per candidate comparison (`contributionIds`, [transfer-matching.ts:340-352](../../../src/app/core/transfers/transfer-matching.ts)) — `resolveTransferMatches` is recomputed by the Dashboard's action-queue panel on every transaction/account/category change, and the co-owner lookup behind the flag normalizes an IBAN on every call.
