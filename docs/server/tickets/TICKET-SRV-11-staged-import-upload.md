# TICKET-SRV-11 — A full-database import is staged to disk, not buffered as a JSON body

- **Area:** Server
- **Released in:** _unreleased_
- **Type:** Bug fix
- **Traceability:** FR-DAT-2 (import a backup); restores the guarantee for a dataset larger than the app-wide body limit

## User story

As someone restoring a backup of several years of transactions, I want the file to upload however large it is, so a restore is not refused with `request entity too large` by a limit that exists to protect the sign-in route.

## Description

`POST /api/data/import` sends the entire backup as one JSON request body, so a restore is bounded by the app-wide `express.json()` ceiling — a limit sized for what an *unauthenticated* caller may make the server allocate, not for a dataset. This ticket splits the operation in two: the bytes stream to a staging file on disk, and the apply step reads that file and runs the existing one-transaction import from local disk.

## Current situation (as-is)

- [`app.ts:41`](../../../server/src/app.ts) mounts `express.json({ limit: JSON_BODY_LIMIT })` — `'10mb'` — **app-wide**, before [`app.ts:49-52`](../../../server/src/app.ts) applies `requireAuth` per router. The body of any request to any path is therefore read into memory and `JSON.parse`'d before a handler decides who is calling, which is why that ceiling has to stay modest: [`network.ts`](../../../server/src/network.ts) binds `::`, so every device on the house network reaches that parser signed out.
- [`data-management.repository.ts`](../../../src/app/core/data-access/data-management.repository.ts) → `importAll` posts `{ mode, data }`, where `data` is the whole export document with every table inlined. It is the one request whose size scales with the user's entire database, and the only one with no ceiling of its own.
- **Root cause of the bare error:** body-parser throws a 413 whose message is `request entity too large`. [`error-handler.ts`](../../../server/src/middleware/error-handler.ts) → `messageOf` passes any 4xx message through verbatim, on the stated assumption that "a 4xx status is only ever set deliberately, by a route that chose both the code and the wording". App-wide middleware is the exception that assumption does not cover, so body-parser's internal prose reaches the user untranslated. [`app.ts:38-40`](../../../server/src/app.ts) predicted exactly this — "a bare 413 rather than anything diagnosable" — and raised the limit instead of removing the failure mode.
- [`category-model.ts:59-61`](../../../server/src/routes/category-model.ts) already solved the same problem for the one other oversized payload, with a per-route parser and its own `ARTIFACT_BODY_LIMIT` of `'64mb'`. The whole-database import never got the same treatment.
- Streaming rows straight into the import transaction is **not** the fix: it would hold a SQLite write lock open across a network upload, so one slow client would block every other request in the house for the duration, and a stalled one would pin the lock until it timed out.

## Desired result (to-be)

- **Two requests, one transaction.** `POST /api/data/import/staged` streams the request body to a file under a staging directory, never buffering it, and answers `{ uploadId }`. `POST /api/data/import` then takes `{ mode, uploadId }`, reads that file, and runs the existing `importDocument` — unchanged — inside its single transaction.
- **The network phase holds no lock, and the transaction crosses no network.** The write transaction covers only local disk → SQLite, which is what makes a database-sized restore safe to allow at all.
- **The bound stays, enforced incrementally.** The staging route counts bytes as they arrive and destroys the request past `STAGED_IMPORT_LIMIT_BYTES`, so there is still a ceiling — just one that never requires holding the body in memory to apply. The app-wide `JSON_BODY_LIMIT` is left exactly as it is, because it is protecting the pre-auth surface and nothing about this ticket changes that.
- **A staged upload belongs to the user who made it.** Another account cannot apply it, and an `uploadId` is a fixed-format token that cannot address a path outside the staging directory.
- **Nothing is left on disk.** The staging file is deleted once the apply step finishes, whether it succeeded or failed, and an upload that is never applied is swept after it goes stale.
- **A refusal says what happened**, in this route's own wording rather than body-parser's.
- The client keeps `importAll(data, mode)`'s signature, so the Replace-vs-Merge dialog, the QR receive path and the schema-version guard are all untouched — one import path, as today.

## Notes

- **The app-wide `JSON_BODY_LIMIT` is deliberately not raised.** Raising it would hand the same allowance to signed-out callers on the LAN, which is the one thing it exists to prevent. The generous ceiling belongs on the one authenticated route that needs it — the shape [`category-model.ts`](../../../server/src/routes/category-model.ts) already established.
- **Compression is a separate, additive win and is out of scope here.** The export document is highly compressible (repeated IBANs, payees and date strings), so `Content-Encoding: gzip` would cut the transfer substantially — but body-parser applies `limit` to the *inflated* size, so it is a speed improvement and not a fix for this bug. Worth its own ticket.
- **The remaining one-shot cost is `JSON.parse` at apply time**, and `res.json()` on the export side, which builds the whole document as a string in memory. Making both constant-memory means a newline-delimited export format — a header line, then one row per line tagged with its table. That is a format change, and [`data.ts`](../../../server/src/routes/data.ts) promises a backup written by the pre-server browser app "imports here unchanged", so both readers would have to live side by side indefinitely. Deferred until staging proves insufficient, which for one household's finances it probably will not.
- **The client still holds the whole document in memory**, because `importAll` is also what the QR receive path calls with an in-memory document rather than a file. Browser memory is not what this ticket is about, and keeping the signature is what leaves the dialog, the QR path and the guard untouched.
- Chunked uploads with server-side reassembly and resume were considered and rejected: that machinery exists for flaky WAN transfers, and this server is reached over a house LAN.
- **Two departures from the `coding-conventions` skill, both deliberate.** First, "a multi-table write is one endpoint, never a sequence of repository calls" — `importAll` now makes two requests, but the rule's invariant is untouched: the staging request writes **no rows at all**, only a scratch file, so the database write is still exactly one endpoint in one transaction and there is no partial state for a failure between the two to leave behind. An abandoned stage costs a swept file. Second, `data-management.repository.spec.ts` cannot use `callApi`, which exists to make "exactly one request" an assertion; it drives `HttpTestingController` directly through one local `stageImport` helper that asserts both requests and hands the apply back unflushed, so a case can fail that half — which is where every refusal the user reads comes from.
- **`STAGED_IMPORT_DIR` is documented in [`server/README.md`](../../../server/README.md)** alongside the other three env vars, stating that nothing in it is worth backing up: a file lives for the seconds between the two requests of one import, and anything left over is swept within the hour.
