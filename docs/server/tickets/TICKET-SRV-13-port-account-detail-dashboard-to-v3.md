# TICKET-SRV-13 — Bring the account-detail dashboard onto the v3 server branch

- **Area:** Server
- **Released in:** _unreleased_
- **Type:** Refactor
- **Traceability:** carries [TICKET-ACC-14](../../accounts/tickets/TICKET-ACC-14-account-detail-dashboard.md) (UI layout spec §4.2, FR-STAT-2..4/6 per account) onto `feature/v3-server-accounts`; must keep TICKET-SRV-06 (hydration over a network that can fail), TICKET-AUTH-02 (sign-out wipe) and TICKET-SRV-10 (no browser storage) intact

## User story

As someone running the self-hosted v3 server, I want the per-account dashboard from the local-first app on my account detail pages too, so that moving to the server does not cost me a feature the browser-only version has.

## Description

TICKET-ACC-14 is built on `main`, where the stores read Dexie. `feature/v3-server-accounts` has replaced that layer underneath the same store API, so the feature should port mostly as-is — but the files it touches (`StatsStore`, the dashboard panels, `range-state.store.ts`, `accounts-detail`) are among the ones v3 has changed most, and v3 adds rules the feature must obey that `main` has never heard of. This ticket brings ACC-14 across and makes it a correct v3 citizen, rather than a merge that compiles. No server endpoint is added: the aggregations stay client-side computeds over hydrated stores, exactly as the Dashboard's do on v3.

## Current situation (as-is)

- `feature/v3-server-accounts` is 24 commits ahead of `main`, and `main` is 1 ahead of it (`c10dacb`, a canvas-stub spec fix). `git diff main HEAD --stat` over `feature-dashboard`, `feature-accounts`, `core/stats` and `core/state` is 42 files — the overlap with ACC-14's footprint is near total.
- On v3, [dashboard-overview.component.ts](../../../src/app/feature-dashboard/components/dashboard-overview/dashboard-overview.component.ts) gates the whole page on `hydrationOf(this.transactionsStore, this.accountsStore)` inside an `mm-hydration-boundary` ([hydration-boundary.component.ts](../../../src/app/shared/ui/hydration-boundary/hydration-boundary.component.ts), [hydration-status.ts](../../../src/app/shared/utils/hydration-status.ts)) so a failed load is an error with Retry, not "No transactions yet" (TICKET-SRV-06). `main` has neither; ACC-14's empty states will be written against plain `hydrated` flags.
- On v3 every stateful store uses `withHydrationState()` + `createHydration` + `registerStoreReset` from [core/store-reset](../../../src/app/core/store-reset/with-hydration.ts) (e.g. [category-comparison-settings.store.ts](../../../src/app/feature-dashboard/category-comparison-settings.store.ts)), and [store-reset-registry.spec.ts](../../../src/app/core/store-reset/store-reset-registry.spec.ts) lists every store with its reason for being wiped on sign-out or not. `main` hand-rolls `let hydration: Promise<void> | null`.
- On v3 [range-state.store.ts](../../../src/app/core/state/range-state.store.ts) is deliberately **not** registered for the sign-out wipe, with that reason written on it — a new `'account-detail'` `RangePageKey` inherits that decision.
- On v3 nothing may persist in `localStorage` / `sessionStorage` / IndexedDB (CLAUDE.md, TICKET-SRV-10); interface state lives in the per-account `uiPreferences` row. Specs on v3 run against repositories over HTTP, not `fake-indexeddb`.

## Desired result (to-be)

- ACC-14's behaviour exists unchanged on `feature/v3-server-accounts`: same sections, same figures, same range independence, same drill-downs, same `'raw'` joint mode, same empty states.
- Account detail's insight section sits inside an `mm-hydration-boundary` fed by `hydrationOf(...)` over every store it reads (at least `TransactionsStore`, `AccountsStore`, `CategoriesStore`, plus `TransfersStore` if the Transfers in / out figure reads transfer rows rather than each transaction's `transferId`), so a failed hydration shows the error-and-Retry state and **never** "No transactions in this range". The balance block and admin actions above it keep their existing v3 gating.
- Any store ACC-14 introduced or changed follows the v3 hydration/reset pattern, and appears in `store-reset-registry.spec.ts` with its reason — or, if it holds no state (a computed-only, component-provided stats instance), the registry's rationale says why it needs no entry.
- Nothing ACC-14 added writes to browser storage. If ACC-14 persisted anything (it should not — ranges are ephemeral, chart options are session-held by `ChartOptionsStore`), it moves to `uiPreferences` through its repository.
- The port lands as reviewable commits on the v3 branch (merge of `main` or a cherry-pick of ACC-14's commits — whichever the history at the time makes cleaner), with conflicts resolved in v3's favour for infrastructure and ACC-14's favour for the feature.

## Acceptance criteria

> **Implementation note (2026-10-18).** Two things the to-be above did not foresee:
>
> - **The boundary needed an extra gate.** Content between `<mm-hydration-boundary>` tags is built by the *page's* template even while the boundary shows its skeleton. On a cold load, transactions finished before categories, so the balance chart mounted detached and echarts sized its canvas to 0 px for good. This was found live, and `account-insights` now renders its content only when `contentShown()` holds. The Dashboard never hit it because its charts are all `@defer (on viewport)`. Recorded as a convention in `coding-conventions/SKILL.md`.
> - **The gate goes through a helper.** It covers `CategoryComparisonSettingsStore`, which lives in `feature-dashboard`, and exporting the store would break the store-placement rule. So `feature-dashboard` exports `statsInputsHydration()` (beside `StatsStore` in `stats.store.ts`) rather than the store itself.

## Notes

- **Needs TICKET-ACC-14** shipped on `main` first. If v3 merges into `main` before ACC-14 is built, this ticket collapses: build ACC-14 directly on the merged code and close this one as superseded.
- **No server work by design.** A per-account stats endpoint was considered and rejected: the Dashboard on v3 already computes everything client-side from hydrated stores, and splitting one page's aggregates between client and server would let the account page and the Dashboard disagree on the same transaction. Revisit only if NFR-PERF-1 is measurably missed.
- No Roadmap or Changelog entry — the Server area's standing rule. ACC-14 carries the user-facing roadmap line.
- Watch `RecurringSeriesStore`, `ForecastStore` and the spending mosaic: they inject `StatsStore` too, and on v3 they sit behind their own hydration gates — the scope token's default must keep them on the root instance there as well.
