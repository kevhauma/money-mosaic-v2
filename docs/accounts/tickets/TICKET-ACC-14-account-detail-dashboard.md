# TICKET-ACC-14 — Account detail becomes a dashboard for that one account

- **Area:** Accounts
- **Released in:** _unreleased_
- **Type:** Feature
- **Traceability:** UI layout spec §4.2 (`/accounts/:id` — "a mini this-month in/out stat pair", never built) and §5 route table (`from`, `to`, `groupBy` on `/accounts/:id`); FR-STAT-2..4 and FR-STAT-6 applied to one account; follows up the gap TICKET-ACC-13's Notes deliberately left open

## User story

As someone with several accounts, I want an account's detail page to show the same income/expense picture the Dashboard shows, but for that account alone, so that I can see what flows through it without mentally filtering the whole-household view.

## Description

`/accounts/:id` today is a balance, a balance chart and the account's admin actions. This ticket gives it the Dashboard's insight layer — stat cards, trend chart, category breakdown, biggest transactions and friends — computed over that account's transactions only, under the page's own date range. It reuses the Dashboard's panels and its pure `core/stats` aggregations rather than forking them. Built against **`main`** (the local-first Dexie app); bringing it onto `feature/v3-server-accounts` is [TICKET-SRV-13](../../server/tickets/TICKET-SRV-13-port-account-detail-dashboard-to-v3.md).

## Current situation (as-is)

- [accounts-detail.component.html](../../../src/app/feature-accounts/components/accounts-detail/accounts-detail.component.html) renders: header (name + Edit / Archive / Clear transactions / Delete), current balance with the TICKET-ACC-13 last-import line, the joint contributions list, and [account-balance-chart](../../../src/app/feature-accounts/components/account-balance-chart/account-balance-chart.component.ts). **No** income, expense, net or category figure for the account exists anywhere in the app, and there is no date-range control on the page — the balance chart borrows the Accounts page's range (`'accounts'`) to set its initial zoom.
- Every Dashboard figure comes from [stats.store.ts](../../../src/app/feature-dashboard/stats.store.ts): a `providedIn: 'root'` signal store whose computeds call `computePeriodStats`, `computeCategoryBreakdown`, `computeWeekdayWeekendSplit`, `computeTopTransactions`, `computeYearOverYearComparison` and `computeCategoryPeriodComparison` over **all** of `TransactionsStore.transactions()`, bounded by `rangeStore.from('dashboard')` / `to('dashboard')`. There is no account parameter at any level of that wiring.
- The panels ([category-breakdown-panel](../../../src/app/feature-dashboard/components/category-breakdown-panel/category-breakdown-panel.component.ts), [weekday-weekend-split-panel](../../../src/app/feature-dashboard/components/weekday-weekend-split-panel/weekday-weekend-split-panel.component.ts), [top-transactions-panel](../../../src/app/feature-dashboard/components/top-transactions-panel/top-transactions-panel.component.ts), [category-comparison-panel](../../../src/app/feature-dashboard/components/category-comparison-panel/category-comparison-panel.component.ts), [trend-chart-panel](../../../src/app/feature-dashboard/components/trend-chart-panel/trend-chart-panel.component.ts)) each `inject(StatsStore)` (or the range store) directly, so they can only ever show the whole-household, `'dashboard'`-range figures.
- [range-state.store.ts](../../../src/app/core/state/range-state.store.ts) — `RangePageKey` is `'dashboard' | 'accounts' | 'explore'`; adding a key is documented as "the whole cost of giving a new page its own range" (TICKET-UI-23).
- [classify-for-stats.ts](../../../src/app/core/stats/classify-for-stats.ts) excludes linked transfers and savings movements from income/expense (FR-TRF-1) and, in its default `'share'` joint mode, weights a joint account's legs by `ownershipShare` and skips co-owner legs.

## Desired result (to-be)

- Below the existing balance block (which stays as it is, actions and all), account detail shows a **range-scoped insight section** for that account:
  - A stat row: **Income**, **Expense**, **Net cash flow**, and **Transfers in / out** for the range. Net worth is not repeated — the balance block above already is that account's "as of today" figure.
  - The **trend chart** (income/expense by category over time, at the page's granularity).
  - **Category breakdown**, **weekday vs. weekend split**, **biggest transactions**, and the **category period comparison** where the range allows one — the Dashboard's own panels, not look-alikes.
  - The balance chart stays, and its initial zoom follows this page's range rather than the Accounts page's.
- The page gets **its own date range**: a new `RangePageKey` (`'account-detail'`), with a range picker in the header's `actions-start` slot next to "Back to accounts" (TICKET-UI-24's scope-control rule). One range for all accounts' detail pages, not one per account; mirrored to `from`/`to` in the URL as the route table in ui-layout-spec §5 already promises.
- **Scoping is a parameter of the shared wiring, not a fork of it.** Recommended shape: the stats wiring reads its scope (`{ rangePage, accountId | null }`) from an injection token that defaults to `{ 'dashboard', null }`; account detail provides a scoped instance in its own `providers`, so the unchanged panels inside it resolve the account-scoped store and the Dashboard keeps the root one. Whatever shape lands, the `core/stats` functions take a pre-filtered transaction list or an `accountId` argument — they are not copied.
- **Whose money it shows — the account's, not my stake.** A joint account's detail page reads its flows at full amount (`jointMode: 'raw'`), consistent with TICKET-ACC-07's "detail shows the real balance, the whole pot". The Dashboard is unchanged and keeps `'share'`.
- **Transfers are visible here, not just excluded.** On the Dashboard an internal transfer nets to zero and is rightly hidden; on one account it is half the story (a savings account would otherwise show €0 in and €0 out forever). Income/expense still exclude linked transfers and savings movements exactly as FR-TRF-1 says; the separate Transfers in / out figure carries them.
- Every stat card and panel drills down (FR-STAT-6) to `/transactions` with `accountId` set alongside the range's `from`/`to`.
- An account with no transactions in the range shows the panels' existing empty states, not zeros dressed up as data; an account with no transactions at all shows one empty state with an "Import transactions" action (preselecting the account if the import wizard supports it).

> **Implementation notes (2026-10-18):**
>
> - **Empty range = one section-level empty state, not the panels' own.** The trend chart panel has no empty state, so letting each panel handle an empty range would draw zeroed charts — the thing the last to-be bullet rules out. An account with transactions but none in the range shows a single "No transactions in this range" state in place of the cards and panels; the balance chart (full history) stays.
> - **No account preselect on "Import transactions".** The import wizard takes no account parameter today, so the button lands on `/import`'s first step.
> - **Scope shape as recommended:** `STATS_SCOPE` (`feature-dashboard/stats-scope.ts`) + `provideStatsScope` (`stats.store.ts`). `AccountsDetailComponent` provides it, and its new child `AccountInsightsComponent` (`feature-accounts/components/account-insights/`) is where the scoped store is first read, because the provider's factory injects the host to read its account id. On `main`, `RecurringSeriesStore` / `ForecastStore` / the mosaic do **not** inject `StatsStore` (the Notes bullet below predates that); only the Dashboard and its panels do.
> - The "Moved to savings" card is dropped as the Notes say; "Transfers in / out" is one card reading `€in / €out`, with the net in its sub-label.
> - **Privacy toggle on a Data page.** The reused panels blur under privacy mode on their own, so the header now carries `mm-privacy-toggle` — the one Data page that does (recorded as an exception in the coding-conventions skill). The balance block stays unblurred.
> - **All-time resolves household-wide.** Picking "All time" on an account page starts from the earliest transaction across all active accounts (`pageRangeControl`'s shared `all-time` resolution), not that account's own first transaction. Accepted as-is: the figures are still that account's, and an earlier start only adds empty buckets.
> - `computeYearOverYearComparison` got the same trailing `jointMode` parameter so the scoped store passes it everywhere, though no account-detail panel reads year-over-year today.

## Notes

- **Not in scope:** the transaction list ui-layout-spec §4.2 also puts on this page. TICKET-ACC-13 flagged it as wanting its own ticket; the drill-downs cover the need for now, and embedding the transactions table is a separate, larger change (pagination, bulk bar, filters).
- **Dashboard panels that don't transfer:** the per-account balance strip (one account — meaningless), the action queue (household-wide to-dos) and the spending heatmap (keep it out unless it scopes for free; it has its own exclusion settings). The Dashboard's customize/reorder mode is not carried over — the detail page has one fixed order.
- **Settings stores that come along:** `CategoryComparisonSettingsStore`'s excluded categories are global and stay global; the trend chart's `chartGranularity('dashboard-trend', …)` key should be scoped (`'account-detail-trend'`) so the two pages don't fight over one granularity.
- `RecurringSeriesStore`, `ForecastStore` and Explore's spending mosaic also inject `StatsStore` — the scope token's default must keep them on the unscoped root instance.
- The "Moved to savings" card is dropped rather than scoped: on one account it is just "Transfers out to savings", which the Transfers card already shows.
- Building on `main` first is deliberate — v3's diff on these files is mostly the TICKET-SRV-06 hydration boundary and SRV-10 settings persistence, which [TICKET-SRV-13](../../server/tickets/TICKET-SRV-13-port-account-detail-dashboard-to-v3.md) reconciles.
