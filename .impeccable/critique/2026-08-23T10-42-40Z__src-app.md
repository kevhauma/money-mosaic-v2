## Design Specificity Verdict

Authored in the copy, generic in the chrome. The writing is unmistakably this product (the Belgian wederbeleggingsvergoeding fee model; "a rhythm can't be read from a single month"; "a bank export only ever shows the net"). The layout is stock admin dashboard: 5-tile KPI strip, donut/treemap/heatmap stack, beige card grid.

The one place the visual system had to be opinionated -- money semantics -- is where it is least authored. Default themes set --color-primary hue 25 and --color-error hue 20: five degrees apart. Brand colour, active-nav pill, current wizard step and negative money are all the same red.

Deterministic scan: essentially clean. 1 finding across 843 files in src/app, and it is a false positive (an assertion string in paper.component.spec.ts:181). Whole-src scan: 9 findings -- 2 bounce-easing in styles.css (active in the shipped default theme, deliberate per the deformable design language), 5 in opt-in pastiche themes (inert), 1 overused-font. The detector and the design review disagree sharply, and that gap is itself the finding: none of the real problems are machine-detectable.

Visual overlays: not produced. The Browser pane was not displayed during Assessment B, so screenshot compositing and script-injection overlay were unavailable. All geometry below is DOM measurement, which is unaffected.

## What's Working

1. Explanatory copy better than most funded products. Sentences that explain why a control is absent, and that pre-empt the exact wrong conclusion each screen invites.
2. Every chart ships an accompanying data table. Consistent, unglamorous accessibility work that survives screen readers, CVD, and canvas failure.
3. Theme contrast is disciplined. Full WCAG AA sweep over every leaf text node on /dashboard in two dark themes: zero failures each. Ten themes including neon-on-black, none leaks an unreadable label.
4. Zero console errors across all 15 routes; clean build, no budget warnings.

## Priority Issues

1. [P0] The numbers contradict each other. Dashboard shows "Savings rate 10.7%" beside "57.1% of income kept"; /future says "€1,600.10/month". Three answers to one question, none labelled with its definition (savingsRate = savings/income counting only money moved to savings accounts; netMargin is documented as different at net-margin.ts:3). Separately, /accounts "Balance history" uses stack:'account-balance' + areaStyle, so each account renders at cumulative height -- reconciling a savings balance against a bank statement yields the wrong number. Violates the product's first principle, correctness over cleverness. Fix: rename tiles to what they measure ("Moved to savings" / "Kept"), put definitions in tooltips, and unstack the balance chart.

2. [P1] Positive net worth renders in the loss red. The tile passes color="primary" as a deliberate hero treatment; the collision is in the palette, not the markup. Default light: primary oklch(68% 0.19 25) vs error oklch(64% 0.21 20). Default dark: 74%/25 vs 70%/20. Only the default themes are affected; of eight custom themes only retro-futurism (14 deg) and memphis (35 deg) are tight. Fix: introduce dedicated money-positive/money-negative tokens and assert a minimum hue distance between primary and error per theme.

3. [P1] Dates are ambiguous to the only user. DEFAULT_LOCALE='en-US' at format-settings.ts:13, and a spec records this replaced a DD/MM/YYYY default. "07/01/2046" on a loan card is unreadable. Fix: default to nl-BE or detect from navigator.language.

4. [P1] The month-end import loop has no safety net. /import step 1 never mentions duplicate detection, lists no prior import, offers no undo. No "last imported" date anywhere. The target user's whole workflow is three overlapping CSVs monthly; the one thing he fears is the one thing the screen never addresses. Fix: import history with per-batch undo, duplicate-count preview before commit, last-imported date on account cards.

5. [P1] The most-used screen visibly collides. /transactions filter form is lg:grid-cols-6 with 115.33px cells. "Amount type" needs 180px, overruns its cell by 65px and overlaps the Min amount field by 53px. No ancestor clips, so it paints on top rather than truncating. The "Make rule from filter"/"Clear" pair needs 176px in 115px and escapes both sides; its right edge (1076) passes the form's (1064). Page gains a horizontal scrollbar (1124 vs 1105). Fix: lg:grid-cols-4 with col-span-2 and min-w-0 on the two offenders.

6. [P2] Destructive actions are understyled and unreversible. /accounts/:id header renders Edit | Archive | Clear transactions | Delete with only Delete in red -- "Clear transactions" wipes 36 rows behind a button that looks like "Archive". Nothing in the app has undo. Fix: move destructive actions to an overflow menu, style as danger, offer "export a backup first" inside the confirm.

7. [P2] Loan card overflows its own border. Row is justify-between with no min-w-0, gap, or truncation in a 201px content box. Measured: amount 320->501.9, caption "remaining" 501.9->559.7, card border 546.3 -- zero gap after the number and 13.4px outside the card. Systematic, not one record: overflows from roughly EUR 1,250 upward; EUR 1,248,392.10 escapes the viewport by 34.7px.

8. [P2] Data-loss risk has no mitigating action. The "Persistent storage: Not active" card ends "this may resolve on its own over time" and offers no button. storage-status.service.ts:8 already calls storage.persist() automatically, so denied means already-asked-and-refused -- a "Request it" button would be dead UI. The only real mitigation is backup, and there is no CTA. The very next card down is "Delete all data", with an error border and a working button.

9. [P2] Step 3 of the core loop is invisible. "Review possible transfers" is a collapsed panel with no count on its trigger; linked pairs still show "Uncategorised" in the Category cell; /explore's Sankey routes the internal transfer as flow in both directions, double-counting it.

## Persona Red Flags

Alex (power user): no skip link (15 tab presses to reach content on every route); no shortcuts, no command palette; /transactions renders all rows unpaginated with a 12-option select inside each; bulk bar is not sticky; two buttons labelled "Clear" ~200px apart; /categories offers "Re-run rules" and "Export all rules" while empty.

Jordan (first-timer): unexplained jargon on first contact ("Match window (days)", "medium-confidence", "Kind: Neutral", "Ungrouped"); "Learning" sits two items above "How-to's" and leads to an ML training console; /import step 1 puts a disabled Back/Next above the drop zone; the stepper's current step is a red circle; /help leaks literal markdown.

Kevin (month-end reconciler, three CSVs): no import history, no undo, no last-imported date; account detail has no transaction list, so "this balance looks wrong" has no answer on the page; balance history double-counts; /recurring lists FreshMarket twice and classifies 100% of the month's spend as recurring with no confidence, merge, or dismiss.

## Minor Observations

Checkboxes compute border-radius 28px on a 20px box, so independent toggles read as a radio group. Sidebar carries 15 links in a 758px menu inside a 700px scroll container -- the last two items need scrolling with no visible affordance, and a code comment still reasons from "nine items". Modal-on-modal for delete confirm with the parent's Save button undimmed behind. Delete confirm identifies the row only as "Supermarket" (8 rows share it). Donut rendered for a single 100% category. "Show more (1)". Heatmap uses per-row scales, so cells are not comparable across rows -- the only thing a heatmap is for. /explore mosaic Share column sums to 110.6%. Account balances render with a leading plus. Payoff date disagrees with itself across two surfaces (07/01/2046 vs August 2046). Settings puts 10 theme cards above currency/locale correctness. Mobile /transactions is a 750px table in a 375px viewport; row checkboxes are 20x20 and icon buttons 24x24 against a 44px minimum; KPI values stay 36px with no responsive type scale. Wordmark says "MoneyMosaic", body copy says "Money Mosaic".

## Questions to Consider

1. Your brand primary and your error colour are the same red, in a product about telling good money from bad. Which one is wrong -- and will you reject any future theme whose primary lands within 20 degrees of the error hue?
2. If this is built for one Belgian user, why does DEFAULT_LOCALE='en-US', and why did a commit deliberately replace a DD/MM/YYYY default?
3. Three surfaces answer "how much do I save?" differently. You know why all three are right. Can the user find out without reading net-margin.ts?
4. /recurring says 100% of this month's spending is recurring, including dinner out, and lists FreshMarket twice. What in the UI lets the user correct it? If nothing, is "reversible automation" a principle or a slogan?
5. Settings ships ten themes and one badge saying the browser might delete every transaction the user owns. Which got more design hours?
